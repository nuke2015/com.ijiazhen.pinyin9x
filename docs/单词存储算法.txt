== 行业通用方案 ==

## 一、核心数据结构对比

Trie(前缀树)       O(k)   较大   前缀补全/输入法         Google Gboard/SwiftKey
DAWG/DAFSA         O(k)   极小   压缩词典/拼写检查       Firefox拼写检查
Burst Trie          O(k)   中等   大规模前缀查询          Lucene旧版
FST                 O(k)   极小   倒排索引/Lucene         Elasticsearch
B-Tree/SQLite       O(logN) 小   小规模通用查询          本项目
双数组Trie          O(k)   中等   中文分词/日文输入       MeCab/Ansj

k=查询词长度, n=总词数
## 二、主流方案详解

### 1. Trie 前缀树

优点: 前缀查询O(k), 天然支持模糊匹配
缺点: 每节点大量子指针, 内存开销大(约10x原文)
优化: Radix Tree(Patricia Trie)合并单分支路径

### 2. FST (Finite State Transducer) -- Lucene方案

行业标杆。Elasticsearch用FST存Term Dictionary。
本质=最小化确定性有限状态自动机, 存key到value映射
百万级英文词库约2-5MB, 支持前缀+正则+编辑距离
共享后缀: running/run/ran共享r-u-n路径

### 3. DAWG (Directed Acyclic Word Graph)

将所有等价状态合并到DAG, 极致压缩
完整英语词典(约20万词)压缩后约500KB
缺点: 不支持value映射(仅判断词是否存在)
DAFSA变体可存词频

### 4. Burst Trie

根节点Trie快速路由, 分支超阈值则叶子用排序数组
兼顾Trie的前缀速度和数组的空间效率

### 5. 双数组Trie (Double-Array Trie)

只用两个数组(base/check)存整棵Trie
查询O(k), 内存紧凑
中文分词(MeCab/Ansj), 英文不如FST灵活
## 三、查询场景选型

移动端输入法       - Trie+词频堆         内存可接受,实时前缀补全
搜索引擎倒排       - FST                 极高压比+前缀+值映射
拼写检查           - BK-Tree/DAWG        编辑距离+内存极小
海量词库           - FST+磁盘分片        Lucene方案
嵌入式/小内存      - 双数组Trie          无指针开销
NLP分词            - 双数组Trie+AC自动机  多模式匹配
小词库(小于1万)    - SQLite LIKE+B-Tree   最简单够用
## 四、Lucene方案(行业最经典)

写入路线:
  原始文本
  -> Analyzer(Tokenizer+Filter)
  -> Token Stream
  -> Inverted Index:
      Term Dictionary (FST: word->postings_offset)
      Postings Lists  (跳表: doc_id, freq, position)
      Doc Values      (列存: 排序/聚合)

查询路线:
  输入 hel
  -> FST.seek 定位到第一个 >= hel 的term
  -> 前缀匹配: FST.next while prefix matches
  -> 从Postings取doc_id列表
  -> 打分排序返回

FST压缩效果(实测): 100万英文term
  原始大小: ~50MB(字符串+指针)
  FST大小:  ~3MB
  压缩比:   ~16x
## 五、对本项目的参考

当前: SQLite LIKE+B-Tree, 约130词, 完全够用

扩展路线:
  1万-5万词:   加idx_word_freq复合索引即可, B-Tree完全胜任
  5万-50万词:  引入FST存term dictionary, SQLite存词频/元数据
  50万词以上:  直接上Lucene倒排索引或独立FST库

当前阶段加个索引就够了, 不需要过度设计。
